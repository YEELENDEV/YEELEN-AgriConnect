## Project

YEELEN AgriConnect — full-stack agricultural management app (French UI/comments/domain vocabulary). React frontend (`src/`) + Express/PostgreSQL backend (`server/`), built and deployed as separate services (see Docker section).

Modules: tableau de bord, calendrier, récoltes, cultures & irrigation (capteurs simulés), poulailler (stocks/ventes/livraisons/suivi), pisciculture (mirroir du poulailler — bassins/stocks/ventes/livraisons/suivi, voir ci-dessous), contacts (clients + fournisseurs unifiés — voir le modèle de données ci-dessous), finances, banques, devis/factures (with e-signature), salariés (RH complet : contrats, présences, congés en self-service, avances, référentiels), équipements (inventaire matériel + maintenance), MFA (TOTP + code email), planning (per-culture intervention plan generation, see below), observations (field notes), météo (prévisions Open-Meteo + alertes agronomiques, granularité entreprise/parcelle, see below), agriculture de précision (analyse de sol SoilGrids + NDVI satellite Agromonitoring, per-parcelle, see below), feedback, aide, recherche globale (Ctrl+K). UI bilingue fr/en (i18n) + affichage montants/dates localisé par entreprise — voir la section « Internationalisation » plus bas.

## Architecture

### Multi-tenant model
Data is partitioned by **company (`entreprise`)**, not by individual user. Key tables: `users`, `entreprises`, and the join table `entreprise_utilisateurs` (`user_id`, `entreprise_id`, `role`, `statut`) — a user's role is scoped per-company, not global. `server/src/routes/auth.js` shows the full lifecycle: `register` creates a `users` row + an `entreprises` row + the linking `entreprise_utilisateurs` row in one transaction; `login` looks up the active `entreprise_utilisateurs` row to determine role/company.

- JWT payload: `{ sub, email, entrepriseId, role }`, signed/verified with `env.JWT_SECRET`.
- `authRequired` (`server/src/middleware/auth.js`) verifies the JWT and sets `req.user`.
- **Authorization (since 2026-11-11)**: no role-text gates anywhere. `permissionGuard` applies the restrictions each entreprise sets on its own roles (`roles` + `role_restrictions`, catalogue in `server/src/permissions/catalogue.js`); the owner (`entreprises.proprietaire_user_id`) is never restricted; an account without an entreprise role is unrestricted. The frontend reads the same restrictions (`GET /api/roles/mes-restrictions`, `src/lib/restrictions.jsx`). The old `requireRole` middleware and the frontend `ROLE_DEFINITIONS` were removed — see the security conventions below and `docs/journal.md` 2026-11-11.
- **Every route handler scopes its queries by `req.user.entrepriseId`** — this is the actual tenant-isolation boundary; there is no other enforcement layer (no RLS, no ORM-level scoping). ### Unified data model (ERP alignment, 2026-08-18) — read before touching contacts/produits/prix
Three earlier split tables were merged as part of aligning the schema on a reference ERP. Full rationale + migration details in `docs/journal.md` (2026-08-18 entries); the essentials:
- **`contacts`** replaces the separate `clients` / `fournisseurs` tables. One row per partner, with a `type` (`client` / `fournisseur` — a contact can be both), company-vs-particulier shape, sub-contacts, and tags (`contact_tags` + `/api/contact-tags`). `GET /api/contacts?type=client|fournisseur` filters. Deleting a contact still referenced by a devis → `409`. The frontend still has distinct **Clients** and **Fournisseurs** tabs, both backed by `/api/contacts`.
- **`produits`** replaces `cultures_stocks` / `poulailler_stocks`. One catalogue, per-row `categorie` (CRUD via `/api/produit-categories`), `prix_defaut`, stock quantity. The Cultures/Poulailler/Pisciculture "Stocks" tabs all read `/api/produits` (filtered by category grouping), and the stock↔achats/ventes sync resolves rows by `produit_id` first, name-match as fallback. **Module Pisciculture (2026-09-05)**: `'Pisciculture'` was added as a third value to the `module` `CHECK` constraint (`produits`, `produit_categories`, `produit_templates`, `achats_documents` — 4 places in `migrate.js`, `DROP CONSTRAINT IF EXISTS`/`ADD CONSTRAINT` idempotent pattern) plus every literal `['Cultures', 'Poulailler']` whitelist in route validation (`produits.js`, `produitCategories.js`, `produitTemplates.js`, `achats.js` ×4) and in `utils/stockSync.js`'s `applyAchatLignesToStock`/`reverseAchatLignesFromStock` (these silently no-op for an unlisted module — no error, just a stock that never syncs, the actual bug class this touches). Built as a structural mirror of Poulailler (see `PiscicultureModule` in `App.jsx`): `StocksTab`/`VentesWithDevis`/`AchatModule`/`ComptabiliteTab` reused as-is with `moduleType="Pisciculture"`; only `BassinsEnvironnementTab` (water-quality gauges: pH/oxygène dissous/température, no backend — pure client simulation, same as `EnvironnementTab`), `PiscicultureMonitoringTab` and `PiscicultureLivraisonsTab` are dedicated components, backed by new `pisciculture_livraisons`/`pisciculture_suivi` tables and `routes/pisciculture.js` — deliberately **not** mirroring Poulailler's own `poulailler_mouvements` ledger, confirmed dead (no frontend caller) and superseded by the devis/achats_documents flow.
- **`listes_prix`** (+ `listes_prix_lignes`) replaces the old per-contact `client_prix`: named, reusable price lists assigned to a contact; `GET /api/listes-prix/prix-effectifs?contactId=…` resolves the effective price (list line → else `produits.prix_defaut`). Detaching a list from a contact is `ON DELETE SET NULL`.

### Multi-devise réel (roadmap, Stage 3/4 — 2026-09-05/06)
Chantier du backlog long terme choisi explicitement par l'utilisateur dans sa version complète/comptablement correcte (comme Odoo : un client peut avoir sa propre devise, un devis/facture peut être émis dans cette devise, le grand livre reste dans la devise de l'entreprise avec écart de change comptabilisé au paiement) — pas la version « affichage seul » plus légère. Vu l'ampleur, staged comme le roadmap ERP Comptabilité initial (6 étapes) : voir `docs/journal.md` pour la roadmap complète en 4 étapes. Recherche (étape 1) : contrairement aux chantiers précédents, Odoo a ici un vrai modèle mature et directement transposable (`res_currency.py` — `debit`/`credit` toujours en devise entreprise, `amount_currency` complémentaire en devise d'origine, taux figé à la date de la pièce) ; `LerianStudio/midaz` (437★) est un vrai grand livre multi-devise mature mais en Go, non réutilisable.
- **Étape 1 (fondations)** : table `currency_rates` (id, devise, taux_vs_usd, date — pivot USD, cross-rate calculé à la volée), alimentée paresseusement (pas de cron) depuis `https://open.er-api.com/v6/latest/USD` (gratuite, sans clé, testée en direct — couvre XOF/XAF et toutes les devises de `DEVISES`, mise à jour 1×/jour, attribution requise dès qu'une UI l'expose). `server/src/utils/currencyRates.js` (`rafraichirTauxDuJour`/`obtenirTaux`/`convertir`), `server/src/routes/devises.js` (`GET /taux?de=&vers=&date=`). Principe central dans `utils/accountMove.js:posterMove`/`enregistrerPaiementMove` : `debit`/`credit`/`balance`/`amount_residual` (le grand livre) restent **toujours** en devise entreprise (converties via `invoiceCurrencyRate`) ; `amount_currency` mémorise le montant en devise du document ; `account_move.amount_untaxed/amount_tax/amount_total/amount_residual` restent en devise **du document** (comme `devis.total`, cohérence de convention). `finances` (miroir en devise entreprise) reçoit systématiquement le montant converti, jamais le brut. Frontend : `FacturesModule` (liste + détail) affiche désormais dans la devise de la facture + ligne d'équivalence — sous-tableaux (lignes/échéances/paiements) corrigés le 2026-09-08, voir « Multi-devise : montants faux hors de l'en-tête » ci-dessous. 1 nouveau test d'intégration complet (facturer + payer en EUR, grand livre vérifié équilibré et converti, `finances` vérifié). **317 tests d'intégration, zéro régression** sur toute la suite Comptabilité existante (factures/factureHash/factureAvoir/paiements/agedReceivable) — le défaut `invoice_currency_rate = 1` rend le nouveau code totalement transparent pour toute facture déjà en devise entreprise. Vérifié en conditions réelles (devis 100 € facturé et payé intégralement → move posté équilibré à 65 595,64 F CFA au vrai taux du jour, `finances` et PDF-adjacent cohérents).
- **Étape 4 (roadmap COMPLETE, 2026-09-06)** : écart de change au paiement, sans aucun nouveau paramètre de route ni changement frontend — `enregistrerPaiementMove` détecte automatiquement `mv.devise !== mv.entrepriseDevise` et convertit au taux du `paymentDate` déjà transmis (via `convertir` de l'étape 1). Deux nouveaux comptes par défaut (`768000 Gains de change`/`668000 Pertes de change`, `income_other`/`expense_other`), backfillés pour les entreprises existantes par `migrate.js:seedComptesChangeForExistingEntreprises`. Le lettrage contre la facture reste au taux **figé** de la facture (jamais rouvert) ; l'écart entre ce taux et celui du règlement ferme le résidu laissé sur la ligne partenaire du paiement via une écriture à 2 lignes (`enregistrerEcartChange` dans `utils/accountMove.js`). **Bug de sens trouvé par débogage empirique (pas par relecture)** : la première version classait le sens gain/perte à l'envers (`estGain = line1Credit > 0`) — corrigé en `estGain = line1Debit > 0` après vérification en conditions réelles (taux inséré en base, ledger relu directement) qu'un débit sur la ligne 1 correspond systématiquement à un gain. 3 nouveaux tests (gain/perte/taux inchangé). **320/320 tests d'intégration, zéro régression.** Détail complet dans `docs/journal.md` (2026-09-06).

### Multi-devise : montants faux hors de l'en-tête (2026-09-08)
Reprise de la « limite connue » laissée par l'étape 3 du multi-devise réel. En vérifiant champ
par champ à la source, ce n'était pas une finition d'affichage : **la balance âgée
(`GET /api/factures/aged-receivable`) sommait des montants de devises différentes sans
conversion**, donc son total était arithmétiquement faux ; `computeMarge` soustrayait un coût
catalogue (devise entreprise) d'un total de devis (devise du devis) ; et **le PDF envoyé au
client suffixait « FCFA » en dur en arrondissant à l'entier**, donc faux pour toute entreprise
non-XOF, pas seulement en multi-devise. Détail complet dans `docs/journal.md` (2026-09-08).

**Le piège à connaître avant de retoucher ces écrans** : `account_move.amount_residual` est en
devise **du document**, alors que `account_move_line.amount_residual` est en devise **de
l'entreprise** (le grand livre) — même dualité pour `account_move.amount_total` vs
`debit`/`credit`/`balance`. Un helper `enDevise(montant, devise)` existe désormais dans
`FacturesModule`, `ComptaReportsPanel` et `DevisModule` ; il ne doit **jamais** être appliqué
aux colonnes débit/crédit, aux montants « à affecter » (issus de
`account_move_line.amount_residual`) ni à la balance âgée (désormais convertie côté serveur au
taux figé de chaque facture), sous peine de réintroduire le bug en sens inverse. Côté PDF,
`formatMontant(n, devise)` et `libelleDevise(devise)` (exportées uniquement pour être testées)
gèrent les décimales par devise et gardent « FCFA » pour XOF seulement, afin de ne pas faire
régresser les documents déjà émis. Le move de paiement porte maintenant `devise` +
`invoice_currency_rate`, sans quoi son `amount_total` (en devise du document) se lisait comme
un montant en devise entreprise.

### Backend structure (`server/src/`)
- `server.js` — thin entrypoint (`testDatabase()` + `listen()`); the Express app itself is the factory `server/src/app.js` (recreated 2026-08-29, shared with the integration test suite). It mounts routes flatly under `/api/*`: `auth`, `business`, `cultures`, `poulailler`, `entreprise`, `salaries`, `banques`, `mfa`, `devis`, `achats`, `observations`, `planning`, `calendar`, `recoltes`, `feedback`, `equipements`, `produits`, `produit-categories`, `contacts`, `contact-tags`, `listes-prix`, `payment-terms`, `taxes`, `journals`, `accounts`, `factures`, `paiements`, `recherche`, `activites`, `messages`, `rh`, `meteo`, `precision`, `devises`. Each route file inlines its own `pg` queries directly — no ORM, no repository layer, no shared query builder.
- `db.js` — the single `pg` `Pool` instance every route imports. **Env loading is centralized in `config/env.js` (2026-11-11)**: it loads `server/.env` then the repo-root `.env` (process env wins), and `db.js` imports it first. Before this, `env.js` only read the root `.env` and was evaluated before `db.js`, so outside Docker `JWT_SECRET` was never found and tokens were signed with the public default `dev-secret-change-me`. `env.js` now refuses to start with `NODE_ENV=production` if `JWT_SECRET` is missing/< 32 chars (dev: warning, or a random per-process secret if absent). `server/babel.config.cjs` rewrites `import.meta.url` for the CJS unit-test runner only.
- `services/` — cross-route business logic: `mailer.js` (nodemailer/Gmail transport: MFA codes, welcome emails, devis emails), `banquesService.js` (bank account CRUD used by `routes/banques.js`), `planningService.js` (`generatePlan`, used by `routes/planning.js`), `cultureService.js` (`getCulturePlanDetails`: looks up a `parcelles` row by id + `entreprise_id`).
- **Fixed 2026-09-05** (was previously a placeholder, see `docs/journal.md`): `cultureService.js` now returns a **real per-culture calendar** — `CALENDRIERS_PAR_CULTURE` (~10 widely-grown crops: Maïs, Riz, Blé, Tomate, Pomme de terre, Oignon, Haricot, Soja, Arachide, Manioc; agronomic day-offsets from semis, written fresh for this project), matched case/accent-insensitively against `parcelles.culture` free text, with the old generic 5-milestone schedule kept as `CALENDRIER_GENERIQUE` fallback for any unrecognized culture. Dates are computed from `parcelles.date_semis` (new nullable column) when set, else from today (unchanged fallback). `POST /api/planning` (`routes/planning.js`) takes `{ cultureId }` — despite the name, `cultureId` is actually a **`parcelles.id`** (there's no separate "culture" table) — and now **persists** each generated milestone as an `activites` row (`ressourceType:'parcelle'`, the existing generic activity model, its `RESSOURCES_VALIDES` allowlist extended to include `'parcelle'`) instead of the old commented-out `savePlanningToDB` TODO. No dedup on repeat calls — a confirm dialog on the frontend button warns before adding more tasks. Frontend entry point added (previously none existed): a collapsible "Plan d'intervention" section inside each parcelle `Card` in `CulturesModule` — a `dateSemis` field (`PUT /cultures/parcelles/:id`, `PARCELLE_COLUMNS` now `to_char`s it to dodge the pg-DATE→JS-Date TZ shift, same fix pattern as `validity_date`/`date_echeance`), a "Générer le plan" button, and `<ActivitesSection ressourceType="parcelle" ressourceId={p.id} />` reused as-is (already generic, previously used only for `'devis'`/`'contact'`). 4 new/updated tests in `planning.test.js` (real per-culture milestones + persistence, `date_semis`-driven dates not "today", unknown-culture fallback, existing 400/404 cases).
- `utils/` — `financeSync.js` (`syncFinanceEntry`/`updateFinanceEntry`/`removeFinanceEntry`/`syncDevisPaiement`: every vente/achat/facture payment writes a mirrored row into `finances`, categorized `Banque` or `Caisse` depending on whether the company has a `banque_principale` set — this is how cross-module financial consistency is maintained, there are no DB triggers), `mouvementHistorique.js` (audit log of edits/deletes on mouvements, written explicitly by routes, read back via `getPoulaillerHistorique`/`getCulturesHistorique`), `devisPdf.js` (pdfkit invoice/quote rendering, streamed to the response).
- `controllers/observationsController.js` (dead code, never imported) was **deleted 2026-11-11**; the live `/api/observations` logic is inline in `routes/observations.js`.
- **Security conventions (audit 2026-11-11)** — reuse these instead of re-inventing them:
  - `middleware/auth.js:signerToken(payload)` is the only way to issue a JWT (HS256 pinned, `JWT_EXPIRES_IN`); verification also pins HS256.
  - `middleware/securite.js`: API security headers, in-memory `creerLimiteur` (per-IP; **disabled under Jest** unless `actifEnTest`), `asyncMiddleware` (wrap any async global middleware — Express 4 doesn't catch rejections), JSON 404 + final error handler (never leaks internals). Mounted in `app.js`: limits on `/api/auth`, `/api/devis/public`, `/api/cameras/alertes`.
  - `app.set('trust proxy', 'loopback, linklocal, uniquelocal')` (override `TRUST_PROXY`); `auditLog.extraireIp` now uses `req.ip` — never read `X-Forwarded-For` raw (it let anyone bypass the 3-registrations/IP limit). Tests still set XFF from loopback, which is trusted.
  - CORS: allowlist `CORS_ORIGINS`/`FRONTEND_URL` + same-origin (Host match) + any localhost outside production.
  - `utils/motDePasse.js`: `validerMotDePasse` (≥ 8 chars, letter + digit, ≤ 72 bytes), `validerEmail`, `BCRYPT_COUT`, `HASH_FACTICE` (constant-time login for unknown emails). Login locks an account after 10 failed passwords / 15 min (`login_locked` audit action).
  - MFA: `/mfa/setup` → 409 if MFA already on; `/mfa/disable` requires `{ password }`; `/mfa/verify` limited to 5 failures/h (`mfa_verify_failed`).
  - Public devis signing only from `Envoyé`/`Devis` (conditional UPDATE, PNG/JPEG data-URL ≤ 500 kB) — the link stays valid after invoicing/cancellation, the old rule let a paid invoice or cancelled quote be re-signed (status back to `Signé` + stock decremented twice).

`server/src/db/migrate.js` is now the **single** source of schema truth — one large, hand-maintained, idempotent script (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`), not versioned beyond this one file. `migrations/001_create_observations_table.sql` at the repo root used to be a second, unconnected mechanism (plain SQL, no runner, had to be applied by hand) — its `CREATE TABLE observations` was folded into `migrate.js` 2026-08-13, so that file is now superseded/historical only; don't apply it separately, everything runs through `migrate.js`.

**Drift risk — the dev DB can be ahead of `migrate.js`.** Because the running `agri_app` DB has accreted columns over time, a route can work locally against a column that `migrate.js` never actually creates, so a *fresh* `docker-compose up` (or the integration-test DB) is broken there. Found 2026-08-30 via the integration suite: `parcelles_historique`, `cultures_mouvements`, `poulailler_mouvements`, `poulailler_livraisons`, `poulailler_suivi` all query/insert `entreprise_id` but their `CREATE TABLE` bodies lacked it and there was no `ADD COLUMN IF NOT EXISTS entreprise_id` — dev had the column from earlier hand-drift, fresh installs 500'd on every cultures/poulailler mouvement/historique/livraison/suivi write. Fixed by adding the 5 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS entreprise_id` + backfill + indexes. Lesson: when adding a route that filters by a column, grep `migrate.js` to confirm that column is actually *created* there, not just assumed to exist because the dev DB has it. The integration suite (which migrates a throwaway DB from scratch each run) is now the guard against this.

Running migrations from the host (rather than `docker exec agri-app-backend-1 node src/db/migrate.js`) requires pointing at the Docker `db` container's host port explicitly (`5433`, see below) — `server/.env`'s `DB_PORT` must stay `5432`, since that's what the **backend container** needs internally to reach `db:5432` over the Compose network (host-side port remapping never affects container-to-container traffic). `docker exec` remains the simplest correct way to run migrations and is what's documented in Commands above.

### Local dev environment on this machine — Docker Desktop, port layout, and a resolved port collision
The app normally runs as 4 Docker Compose services (`docker-compose up --build`):

| Service | Image/build | Host port | Notes |
|---|---|---|---|
| `db` | `postgres:18-alpine` | **`5433:5432`** | app data lives here (host port intentionally *not* 5432 — see below) |
| `backend` | `./server` (Dockerfile) | `4000:4000` | `DB_HOST` overridden to `db` (Compose network) in `docker-compose.yml`; `DB_PORT` stays `5432` (container-internal, from `server/.env`) — these are independent of the host-side `5433` mapping |
| `frontend` | root `Dockerfile` (Vite build → nginx) | `8090:80` | `VITE_API_URL` baked in at build time |
| `backup` | `server/Dockerfile.backup` | *(none published)* | `pg_dump` every 6h, see Backups above |

**There is also a native Windows PostgreSQL service (`postgres.exe`) permanently listening on port 5432 on this machine, independent of Docker** — confirmed by querying it directly (a different, smaller dataset than the app's real data). `db`'s host port was deliberately moved to **`5433`** (2026-08-12) to stop colliding with it. Consequences:
- **pgAdmin** (or any host-side tool/script) must connect to `localhost:5433` for the real app database — `localhost:5432` is now unambiguously the native Windows Postgres, not Docker's.
- Container-to-container traffic (backend → db) is unaffected either way — it always uses the container-internal port 5432 regardless of the host mapping, which is why no other file needed to change for this fix.

### Backups
`server/Dockerfile.backup` + `server/backup.sh`: a sidecar container loops forever, running `pg_dump` every 6 hours into `/backups`, keeping only the 14 most recent dumps. `backups/` and `agri_app_backup.dump` at the repo root (both gitignored via `*.dump`/`backups/`) are artifacts of this/manual dumps, not something the app reads at runtime — corrected 2026-08-16, this file was never actually committed despite an earlier note here claiming otherwise.

**Verified restorable (2026-08-12)**: restored the latest dump into a throwaway database (`pg_restore` inside the `db` container) and confirmed row/table counts matched the live DB exactly. The restore mechanics work.

**Found and fixed (2026-08-12): silent empty-dump failures.** 3 of the last 14 rotated dumps were 0 bytes — `backup.sh` didn't check `pg_dump`'s exit code robustly (`set -e` alone wasn't catching it in practice) or verify the output file was non-empty, so failed backups were silently kept and rotated in as if valid. Likely cause: `backup`'s `depends_on: - db` (old short form) only waited for the `db` *container* to start, not for Postgres inside it to actually be ready — a classic cold-start race. Fixed:
- `docker-compose.yml`: `db` now has a `healthcheck` (`pg_isready`); `backend` and `backup` now `depends_on: db: condition: service_healthy` instead of the old unconditional form.
- `server/backup.sh`: now explicitly checks `pg_dump`'s exit code and that the resulting file is non-empty (`[ -s "$BACKUP_FILE" ]`) before declaring success; deletes and fails loudly (`exit 1`) otherwise instead of leaving a useless 0-byte file in the rotation.
- The 3 pre-existing empty dumps were deleted from `backups/`.

**Alerting + automated restore-test added 2026-08-29** (`server/backup.sh`). Since this container is a bare `postgres:18-alpine` (no node → no access to the app `mailer`), "alerting" is **sentinel files** in the host-mounted `./backups/`, meant to be watched by an operator or a future check:
- `.last_success` — rewritten (timestamp + size) on every successful dump.
- `.last_failure` — written (timestamp + reason) whenever `pg_dump` fails or produces an empty file; **removed** on the next successful dump. Its presence = a dump is currently broken.
- `.last_restore_test` — result of the last restore test, `"<ts> OK …"` or `"<ts> FAIL …"`. Not written to `.last_failure` (which a later good dump would wipe, masking it) — a leading `FAIL` here is its own alert.
- Restore test: runs at most once per `RESTORE_TEST_INTERVAL_HOURS` (env, default 168 ≈ weekly; checked via `find -mmin` on `.last_restore_test`), **after** the dump+rotation and never blocking them (`run_restore_test || true`). It `createdb agri_app_restore_test` → `pg_restore` the newest dump → compares table count (schema `public`) + `users` + `entreprises` row counts against the live DB → `dropdb`. `rc != 0` from `pg_restore` **or** any count mismatch → `FAIL`. `DB_USER` is the Postgres superuser (`POSTGRES_USER`), so create/drop are allowed.
- Verified end-to-end against the local stack: normal cycle writes `.last_success`; forced restore test passes (`tables 54/54 users 13/13 entreprises 9/9 rc=0`) and drops the throwaway DB; a simulated `pg_dump` failure (bad `DB_NAME`) writes `.last_failure` + `exit 1` without touching `.last_success`; the next good cycle clears `.last_failure`.

Still not done: turning the sentinel files into a real push alert (email/webhook) — deferred until hosting + SMTP exist; the files are the interim mechanism. `Dockerfile.backup` and `docker-compose.yml` unchanged (the 6h loop and env are the same; `RESTORE_TEST_INTERVAL_HOURS` can be set on the `backup` service if the weekly default needs tuning).
